# 关系型数据库

MySQL 和 PostgreSQL 是常见的关系型数据库。这篇笔记重点讨论两种扩展手段：**复制** 与 **分区**。

## 复制：定义与角色
复制：在不同机器上存储同一份数据的多个副本。MySQL 中常见的单主复制由主库（primary，旧称 Master）写入，副本（replica，旧称 Slave）同步主库的变更。

## 复制：binlog 与配置
在单主复制中，更新、插入、删除或修改表结构的操作通常发送到主库。

主库把已提交的变更记录到 binlog。binlog 可以记录行级变更或 SQL 语句；副本通过 binlog 位置或 GTID 跟踪同步进度，并读取后续变更。

MySQL 内置复制功能。下面是传统配置的简化示意；实际部署还需要复制账号、权限等设置，较新版本也提供 `SOURCE` / `REPLICA` 术语与 GTID 配置。

Master服务器上：
```
log_bin=mysql_bin
server-id=1
```

Slave服务器上：
```
log_bin=mysql_bin
server-id=2
```
并且指定master服务器：
```
CHANGE MASTER TO MASTER_HOST='xxxx', MASTER_USER='xxxx',
MASTER_PASSWORD='password', MASTER_LOG_FILE='binlog_file',
MASTER_LOG_POS=log_file_position;
```

## 复制：工作流程

首先，客户端向主库提交数据修改；事务提交后，变更进入主库的 binlog，主库可以返回成功响应。

副本从上次同步的 binlog 位置或 GTID 继续获取变更。主库将后续 binlog 事件发送给副本。

副本先将收到的事件写入中继日志（relay log），再按顺序应用到本地数据集，同时更新复制进度。

常见的异步复制不会等待副本应用变更就向客户端确认，因此副本可能暂时读到旧数据。复制延迟不是固定的 50–500 ms；负载、网络和副本处理能力都会影响它。


## 主从复制：拓扑
一台主库可以连接多个副本。增加副本能扩大读取容量，但复制流量也会给主库带来一些开销。

每个副本独立跟踪自己的复制进度；一个副本故障通常不会直接影响其他副本。


## 主从复制：用途

+ 备份：可以在副本上执行备份，减轻主库的备份负担；复制本身不等于备份。
+ 读写分离：允许在更多服务器之间分配只读语句,从而在更多机器之间共享负载。因为添加了更多相同数据的副本以增加读取容量。
+ 查询隔离：允许将不同的Slave服务器用于不同类型的查询。例如,可以将一个Slave服务器用于常规应用程序查询,另一个Slave服务器用于慢速、长时间运行的报告。通过为慢速查询使用单独的Slave服务器,可以使应用程序与I/O密集型查询隔离,从而改善整体用户体验。
+ 故障转移：如果Slave服务器出现故障,可以简单地停止向该服务器发送请求(将其从轮换中取出),直到它被重建。失去Slave服务器并不是什么大事,因为Slave服务器没有任何无法通过Master服务器或其他Slave服务器获得的信息。
    + MySQL服务器不会跟踪彼此的可用性,因此必须在数据库客户端执行服务器故障检测。可以在应用程序逻辑中实现它,或者使用智能代理/负载均衡器来检测Slave服务器故障。

## 主–主复制（多主）
主库故障时，不能只把写流量指向一个副本：还要确认复制进度、提升新主库、防止旧主库恢复后继续写入，并重新配置其他副本。

主–主复制让两个节点都可以接受写入，并相互复制变更。系统需要避免事件循环；如果两边同时修改同一条数据，还必须处理写入冲突。实际系统常限制某些数据只在其中一侧写入，以降低冲突风险。


### Master服务器故障转移

一种部署方式是让节点 A、B 各自连接副本。A 故障后，可以将写流量切到 B，但切换前要确认 B 的数据进度，并防止 A 恢复后继续接受写入。

因为两边都保存完整数据集，存储和索引成本也会增加。

### 主–主复制的扩展限制
+ 两个Master服务器都必须执行所有写入。由于每个Master服务器也是Slave服务器,因此它首先将复制的语句写入单独的中继日志,然后执行该语句,导致额外的磁盘I/O。
+ 两个Master服务器具有相同的数据集大小。由于两个Master服务器具有完全相同的数据集,因此两个Master服务器都需要更多内存来容纳不断增长的索引并在缓存中保留足够的数据集。


## 故障处理

### Failover 故障转移
1. 冗余部署
2. 故障检测 (需要在客户端侧实现或者依靠智能代理)
3. 路由切换

### Disaster recovery 故障恢复
使用复制的主要原因之一是通过减少替换损坏数据库所需的时间来提高可用性。
+ Slave服务器故障：流量切换，到另一台Slave服务器（会暂时降低总的容量，直到重建Slave服务器）
+ Master服务器故障：原生的异步主从复制本身不会自动把副本提升为主库。可以使用故障检测与切换工具；InnoDB Cluster（Group Replication + MySQL Router）是另一种高可用方案。

## 复制的局限性
1. 在常见的单主设计中，复制主要扩展读取；主库仍承受全部写入。
2. 复制延迟：副本可能返回陈旧数据（stale data）。
3. 需要处理故障切换、监控和更多机器的成本。


## 数据分区
**Sharding / data partitioning**

数据分区背后的核心动机是将数据集划分为更小的部分,以便可以将其分布在多台机器上,从而没有任何服务器需要处理整个数据集。

通过将数据集划分为更小的存储桶并将每个存储桶分配给一个分片，每个分片负责自己的数据。单分片操作通常不需要与其他分片协调；跨分片查询和事务仍可能需要协调，某个分片故障也会影响它负责的数据。


### 关键在于选择sharding key
分片的核心思想是以某种方式划分数据,以便每个服务器只获得其中的一部分。分片键是用于决定哪个服务器负责正在查找的数据的信息。
一旦知道哪个服务器拥有数据,就可以连接到它并发出查询。需要访问数据以读取或写入数据时, 能够在不询问所有服务器的情况下定位数据所在的分片。

一个简单的方式是根据用户ID将每个用户分配给单个数据库服务器。
访问用户的数据时,都会获取用户ID并检查它是奇数还是偶数,以找出该用户属于哪个数据库服务器。一旦知道服务器编号,只需连接到它并执行数据库查询,就像它是常规数据库一样。

执行分片,最好将数据集拆分为大小相似的存储桶,因为这有助于在服务器之间均匀地分布数据。

### 分片的优点

1. 如果分片键选择得当，可以通过增加分片扩展存储和写入容量。
2. 可以在应用程序层实现它,然后将其应用于任何数据存储,而不管它是否开箱即用地支持分片。

### 分片的缺点
1. 跨分片查询和 JOIN 无法像单库查询一样直接完成，可能要在多个分片执行部分查询，再合并结果。跨分片事务也需要额外机制来保证一致性，不能直接依赖单库事务的 ACID 保证。
2. 随着数据的增长,可能需要添加更多服务器(分片)。
