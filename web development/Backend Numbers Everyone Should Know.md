# Backend Numbers Everyone Should Know

**Q：如何做好 back-of-the-envelope estimation（数量级估算）？**

**A：先用基础数字和公式推出数量级，再用真实系统的监控数据校准。**

Peter Norvig 的数量级估算思路，以及常与 Jeff Dean 关联的 `Numbers Everyone Should Know` 清单，都在提醒我们：先掌握内存、磁盘和网络操作的大致耗时，再从基本假设推导。估算时不必记住每个精确数字，更重要的是说清楚**请求做了什么、瓶颈是什么、假设是什么**。下表都是数量级参考，不是任何机器都能达到的固定性能。

## 1. 延迟量级：先有时间感

| 操作 | 粗略耗时 |
| --- | ---: |
| 3 GHz CPU 的一个周期 | 约 0.3 ns |
| L1 / L2 cache 访问 | 约 1 ns / 4 ns |
| 内存 DRAM 访问 | 约 100 ns |
| 进程内函数调用或小对象分配 | 几十到几百 ns 起；随语言和运行时变化很大 |
| 本机进程间通信 | 几 μs 起 |
| SSD 随机读 | 约 100 μs；设备和云盘类型会改变这个数字 |
| SSD 顺序读 1 MB | 约 0.1–1 ms；主要由吞吐量决定 |
| 同机房内网 RPC 往返 | 约 0.2–1 ms |
| 机械盘随机读（含寻道和旋转） | 约 5–10 ms |
| 同城或跨机房 RPC 往返 | 几 ms 到十几 ms |
| 跨洲网络往返 | 约 100 ms 量级 |

**记忆顺序：CPU/cache < 内存 < SSD < 机房内网络 < 机械盘随机读或远距离网络。** 一个 HDD 随机读可能比一次内存访问慢约十万倍；具体比例会因设备和访问方式变化。

CPU 和内存操作也有成本；不能因为单次访问快，就忽略大量计算、内存分配或缓存未命中。多加一层网络调用也会增加延迟，尤其要看串行调用次数和 p95/p99 尾延迟。

## 2. 磁盘与数据库：从 IOPS 估 QPS

- **IOPS**：设备每秒能完成多少次 I/O 操作。
- **QPS**（queries per second）：每秒处理多少次查询。
- 如果一次查询平均要做 `k` 次随机磁盘 I/O，且磁盘是瓶颈，那么 `QPS ≈ 可用随机 IOPS ÷ k`。

| 场景 | 假设 | 粗略结果 |
| --- | --- | ---: |
| 机械盘冷读 | 150 随机 IOPS；每查询 3 次随机 I/O | 约 50 QPS |
| SSD 冷读 | 20,000 随机 IOPS；每查询 3 次随机 I/O | 约 6,700 QPS |

典型单盘随机 IOPS 可以暂记为：机械盘约 **100–200**，普通 SSD 约 **1 万–10 万**。多盘有机会提高总 IOPS，但还会受控制器、队列深度、数据库并发等因素限制。

这个公式只适合解释**受随机磁盘 I/O 限制的冷读**。热数据可能直接命中数据库内存缓存；写入还涉及日志、刷盘、批量合并、锁和复制，不能用冷读结果断言“数据库最多只能写 50 QPS”。真实 DB 吞吐量也取决于索引、SQL、JOIN、排序及缓存命中率。

## 3. Cache：吞吐量与容量

远程缓存（如 Redis、Memcached）的一次简单请求，机房内网络往返可能在 **0.2–1 ms** 量级。**RTT 不是单机吞吐量上限**：多个连接可以并发等待网络响应，最终还要看每请求 CPU 时间、网卡、数据大小和实现方式。

用 CPU 做一个粗估：

```text
QPS ≈ CPU 核数 × 每核每秒 CPU 时间 ÷ 每请求 CPU 时间 × 目标利用率
    ≈ 4 × 1000 ms ÷ 0.1 ms × 0.8
    ≈ 32,000 QPS
```

这里假设 4 核、每请求消耗 0.1 ms CPU、目标利用率 80%。这是**示例计算**，不是 Redis 或任何缓存服务的保证值。

也可以用并发量和端到端延迟做另一种估算：若只有 **8 个并发中的请求**，每个请求平均需要 **0.5 ms**，则吞吐量约为 `8 ÷ 0.0005 = 16,000 QPS`。这里的 `8` 是并发请求数，**不能直接把 8 核 CPU 当成只能处理 8 个并发请求**。

容量也可以先算原始数据：`1 GB ÷ 200 B/条 ≈ 500 万条`。实际每条还有 key、对象元数据、内存分配和碎片开销，因此可能只能稳定放 **约 200 万–300 万条**；具体要根据数据结构和实测内存用量调整。

## 4. Application Server：多少 QPS 算高？

单机能处理多少 QPS，取决于每个请求消耗的 CPU、数据库访问次数、外部调用和响应大小。**没有通用的“1000 QPS 分界线”。** 先按下面的公式估算，再用压测验证：

```text
单机 QPS ≈ CPU 核数 × 1000 ms × 目标利用率 ÷ 每请求 CPU 毫秒数
所需实例数 ≈ 峰值 QPS ÷ 单机可持续 QPS
```

例如，一个服务总流量为 **200 QPS**，平均分到 **3 台** 服务器，每台约 **67 QPS**，CPU 各为 **20%**。如果 CPU 使用随流量近似线性增长，目标 CPU 为 **80%**，则每台约能到 `67 × 80% / 20% ≈ 267 QPS`。这只是从该观测推出的粗估，不能直接断言“每台约 500 QPS”：数据库或外部服务可能先成为瓶颈，延迟也可能先超标。

流量增加时，要一起看 **CPU、p95/p99 延迟、错误率、队列长度和下游资源**。接近容量上限时，排队会让尾延迟快速上升；但“QPS 增加 30% 就一定变慢”不是固定规律。

## 5. 做一道估算题的顺序

1. **定义请求：** 一次请求查几次数据库？读多少字节？有多少串行 RPC？
2. **算平均和峰值：** 例如 `日请求量 ÷ 86,400` 得平均 QPS，再按业务峰值倍率估峰值。
3. **找瓶颈：** 分别估 CPU 时间、磁盘 I/O、网络带宽和下游容量，取最先到上限的一项。
4. **留余量并实测：** 为突发流量、故障切换和尾延迟留空间，再用压测及生产指标修正假设。

**应用到方案选择：** 如果读多写少且数据库吃力，先检查慢 SQL 和索引；适合缓存的数据再考虑 cache 或只读副本。如果瓶颈是主库写入，读缓存无法直接解决，需要分析写路径、批处理或分片等方案。
