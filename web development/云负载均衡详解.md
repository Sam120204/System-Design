# 云负载均衡详解

**一句话：** 负载均衡器（Load Balancer，LB）站在客户端和多台服务器之间，把请求送到合适且健康的服务器。

```text
客户端 → 负载均衡器 → 服务器 A
                    → 服务器 B
                    → 服务器 C
```

这样，客户端只需要访问一个入口，后端服务器可以增加、减少或替换。

## 它做哪三件事？

| 功能 | 简单理解 | 例子 |
| --- | --- | --- |
| Endpoint discovery（发现后端） | 知道当前有哪些服务器可以接请求 | 自动扩容新增一台 VM，LB 把它加入后端列表 |
| Health check（健康检查） | 定期确认服务器能否正常服务 | `/health` 连续检查失败，就暂时不再向它发送新请求 |
| Load balancing（分配流量） | 在健康服务器之间选择一台 | 轮询、按权重分配，或选择当前连接较少的服务器 |

一个请求的大致过程：**发现后端 → 排除不健康的后端 → 按规则选择一台 → 转发请求**。故障服务器恢复健康后，可以重新加入后端列表。

## L2、L4、L7 到底有什么区别？

截图中的 OSI 七层模型不必全部背下来。理解云负载均衡，先记住它依据什么信息做决定：

| 层 | 主要看什么 | 与负载均衡的关系 |
| --- | --- | --- |
| L2 数据链路层 | 同一局域网内的帧、MAC 地址 | 截图中的 Ethernet frame 属于这一层；通常不是 Web 服务选择云 LB 时的重点 |
| L4 传输层 | IP、端口、TCP/UDP 连接 | 可以把连接分给不同服务器，但不会按 HTTP 路径区分 `/video` 和 `/images` |
| L7 应用层 | HTTP 请求的域名、路径、请求头等 | 可以根据 URL 等内容，把不同请求送到不同后端服务 |

**记忆方法：L4 看“连接要去哪台机器”；L7 还能看“这个 HTTP 请求要哪个服务”。** L7 建立在底层网络连接之上，并不是跳过 L4。

## 截图中的 L7 例子

```text
内部客户端
    ↓
内部 HTTP(S) 负载均衡器
    ├─ /video  → Video VMs
    └─ /images → Images VMs
```

LB 先根据路径选择**后端组**：`/video` 去视频服务，`/images` 去图片服务；然后在该组健康的 VM 中选择一台。“内部”表示这个入口供私有网络内的客户端访问，不直接面向公网。

## 为什么在云上特别有用？

云服务器经常自动扩缩容，也可能故障或被替换。LB 会更新后端列表、避开不健康的机器，并把流量分给仍可用的机器。**LB 负责分配流量；真正处理请求的容量仍来自后端服务器。**

> 面试简答：云负载均衡器发现后端、检查健康状态，再把流量分配给健康实例。L4 根据连接信息转发；L7 还能根据 HTTP 路径等内容路由到不同服务。
