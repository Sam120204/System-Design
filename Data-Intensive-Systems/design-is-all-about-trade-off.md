# design is all about trade-off

有几个问题，我听见过很多次：

1. 看了很多 system design 的资料，但是觉得学来学去都是理论知识，缺乏动手的经验，最后还是似懂非懂
2. 工作中参与大项目的经验少，平时都是做产品/infra/pipeline/xxx（某个单一方向），怎么办？
3. 用过 AWS ( APIGateway, Route53, EC2, ECS Cluster, ECR, DynamoDB, S3, Lambda, SQS, SNS, VPC Peering，websocket等)，对各部分有了解，但没有深入trade off，缺乏巨量数据的处理经验, 怎么办？

......

其实都是同一个误区：“为什么我已经读了资料/参与了产品/使用了云组件，但还是不能做好 system design？”

这里最大的gap，在于过于依赖输入，而输出太少。

system design 依赖你的工作经历，但大部分经历不是来自于项目实施，而是与参与方的沟通（aka 跟不同组吵架）。

我们说design is all about trade-off，大部分时候我们要做的是平衡各方的利益（aka 相互甩锅）。

一个模拟场景，比如你负责的某个服务一到中午QPS就上升，延迟增加。你意识到这是因为大家会在中午刷手机，所有后端撑不住。于是你想我先扩容一下。

到这里你只是给出了一个solution, 真正的design是从吵架开始。

1. 你的老板不同意你的方案，问你为什么要扩容。扩容你要增加服务器，过了中午这段时间服务器空转，浪费资源，那你是不是还要减少服务器？你为什么不用message queue缓冲一下？（你的老板给出了trade-off, 指出你方案的劣势，和另一种方案的优势）
2. 你觉得老板说的有道理，于是你改了一下，打算加个kafka. 这时候运维组跑过来问你，谁让你加Kafka的，你加了Kafka谁来管理？运维组觉得跑的好好的，能不动就不动。（你的stakeholder和你产生了利益冲突，你减少了自己的问题，但是增加了他们的工作压力）
3. 你的方案被挡回去，你去找你的老板，你的老板说，咱们直接上云，用Amazon SQS，让AWS负责管理。但是运维组拉来了他们的VP表示,现在经济不好，咱们没钱上云，你们业务组自己修吧。

......

这种吵架每个公司每天都有。当你观察一个系统为什么最后会演化成我们看到的样子，背后发生的每一次吵架都是design trade-off.

好的系统是演化出来的，而不是设计出来的。你需要更多的参与演化的过程（参与更多的吵架 甩锅），真正写代码能提供的视角只占一小部分。

有一种练习 trade-off方法叫做Devil’s Advocate，站在“反对者”立场，不断挑刺、找边界条件、放大风险，倒逼方案把 trade-off 讲清楚、把漏洞补上。

我建议自己扮演challenger的角色，重新审视自己的项目。比如你使用SQS，那这个设计最核心的 SLO是什么？延迟/一致性/可用性哪个第一？峰值流量怎么来？有没有尖峰/热点/节假日？哪些是“必须正确”，哪些允许“看起来不对一会儿”？数据模型怎么保证不被写崩？主键/唯一约束/索引会不会爆？到底需要强一致还是最终一致？用户看到“错”的场景是什么？分区键是什么？会不会分片倾斜？QPS 翻 10 倍，哪一层先炸？怎么水平扩展？依赖挂了怎么办：DB / cache / MQ / 下游服务各挂一次怎么容灾？重试会不会放大故障？幂等怎么做？去重 key 是什么？……

当你能说出: “我优先保证 X（SLO），所以选 A；缺点是 Y；为此我加了方案B作为 mitigation；当指标到 Z 我会切到 C….” 就掌握trade-off了
