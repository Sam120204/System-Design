# 异步系统设计复习：Kafka、Queue、Pub/Sub 与事件日志

## 从零理解 Pub/Sub

**Pub/Sub = Publish / Subscribe，即发布／订阅。** 发布者（Publisher）把消息发到一个主题（Topic），订阅者（Subscriber）事先声明“我关心这个主题”，消息系统再让各个**独立订阅**都能处理这条消息。发布者不用逐个调用订阅者，也不必知道目前有多少订阅者。

例如用户支付成功，订单服务发布一次 `PaymentSucceeded`：

```text
订单服务 → 发布 PaymentSucceeded 到 payments 主题
                              ├─ 邮件服务的订阅 → 发送收据
                              ├─ 积分服务的订阅 → 增加积分
                              └─ 数据分析的订阅 → 更新报表
```

订单服务只发布**一条事件**，三个下游各做自己的事。邮件服务暂时处理很慢，不应要求积分服务也等它；各订阅分别追踪自己的处理进度。这就是 Pub/Sub 中“一对多”的含义。

它与**工作队列**的区别在于“谁需要处理同一条消息”：

| 场景 | 同一条消息的处理者 |
| --- | --- |
| 工作队列：`SendReceiptEmail` | 邮件 Worker A、B、C 分摊任务，通常其中一个完成这封邮件。 |
| Pub/Sub：`PaymentSucceeded` | 邮件服务、积分服务、分析服务**各处理一次**，因为它们要做不同的事。 |

注意“每个订阅者各处理一次”说的是**每个独立订阅／服务**，不是服务中的每台机器都处理一次。例如邮件服务有 5 个 Worker，它们共同分摊邮件服务收到的事件，不能因此发出 5 封相同的收据。出现故障重试时，同一订阅仍可能重复收到事件，所以业务处理需要幂等。

## Kafka 是干什么的？

Kafka 是一个**持久保存并分发大量消息的事件流平台**。业务服务把事件写进去，其他服务按自己的进度读取。它常用于服务之间传递业务事件、收集日志／埋点、数据库 CDC、实时分析，以及需要重放历史消息的场景。

可以先记住四个词：

1. **Topic（主题）**：消息按类别存放的地方，例如 `payments`。订单服务把支付事件写入这个 Topic。
2. **Partition（分区）**：一个 Topic 拆成多个有序日志，以提高吞吐和并行处理能力。Kafka 保证的是**单个分区内**的顺序，不是整个 Topic 的全局顺序。
3. **Consumer Group（消费者组）**：一个下游服务的一组读取者。邮件、积分、分析各建一个组，就都能独立读到 `payments` 的事件；邮件组内的多个 Worker 则分摊分区。
4. **Offset（读取位置）**：组在某个分区读到哪里。邮件组读得慢，不会改变积分组的 Offset。

Kafka 接到消息后会把它追加到 Topic 的分区日志中，并按配置保留一段时间。消费者读取并提交 Offset，**不会把消息从 Kafka 删除**。只要旧消息还在保留范围内，消费者就可以调整读取位置重放。因此 Kafka 既能支持上面的 Pub/Sub，也能让一个消费者组分摊任务；但如果只是简单的逐任务确认、延迟重试和死信处理，普通任务队列往往更直接。

## 先回答：Kafka 属于 Message Queue 还是 Pub/Sub？

**两种用法都可以，但 Kafka 的底层模型是分区化的持久事件日志。** Queue 和 Pub/Sub 描述的是消息如何被消费者处理的工作模式；Kafka 是实现这些模式的一种数据系统。

- **当任务队列使用**：把 `ResizeImage` 发到 Topic，一个消费者组中的 Worker 分摊各分区的任务。对同一条消息，正常情况下组内只有一个 Worker 负责处理，呈现工作队列语义。
- **当发布／订阅使用**：把 `OrderCreated` 发到 Topic，风控、统计和通知各用独立的消费者组读取。每个组都有自己的消费进度，彼此不影响，呈现 Pub/Sub 语义。
- **作为事件日志使用**：事件按保留策略留在 Topic 中；消费者可在保留范围内从历史 Offset 重新读取。**消费成功不会删除 Kafka 中的消息**。这也是它与普通工作队列的重要区别。

因此，判断系统设计时，先问“消息表达什么”和“消费者怎样读取”，再选 Kafka、SQS、RabbitMQ 或其他产品。

## 一、维度一：消息的语义

| 语义 | 它说的是什么 | 例子 | 主要关注 |
| --- | --- | --- | --- |
| **Event（事件／事实）** | 已经发生了什么 | `OrderCreated`、`PaymentSucceeded` | 事实记录、多个下游独立反应、追溯与重放 |
| **Command（命令／任务）** | 希望有人做什么 | `SendEmail`、`ResizeImage` | 谁负责执行、成功确认、失败重试与最终失败 |

**Event** 的事实不依赖某个消费者是否在线。例如订单已经创建，即使此刻没有统计服务，事件仍应被可靠记录。这里的“应记录”是业务设计要求；它并不意味着每个事件都要永久保留。数据库 WAL／Binlog 与业务事件日志都能记录变化，但二者的内容、保留期和外部消费能力并不相同。

**Command** 指向待完成的动作。如果没有执行者或最终执行失败，就需要让调用方或运维系统知道这个结果。Command 的接收者可以是一组竞争 Worker，也可以是明确的某个服务；不必把 Command 和“只能有一个物理消费者”画等号。

同一业务流程可以两者并用：`PaymentSucceeded` 是事实；通知服务收到它后生成 `SendReceiptEmail` 任务。前者可以供多个系统读取，后者需要被一个 Worker 完成。

## 二、维度二：消息的传递与读取模式

| 模式 | 谁读取同一条消息 | 典型用途 | 常见关注点 |
| --- | --- | --- | --- |
| **工作队列（1-to-1）** | 一组 Worker 分摊；每次交付给一个 Worker | 图片处理、邮件任务、异步作业 | ACK、重试、死信、负载均衡 |
| **发布／订阅（1-to-many）** | 多个独立订阅各获得一次处理机会 | 订单事件同时通知风控、统计、积分 | 订阅管理、每个订阅的独立进度 |
| **持久日志（0-to-N 读取）** | 生产者追加消息；0 到多个读者按位置读取 | CDC、审计、事件流、历史重放 | 分区、Offset、保留期、回放 |

这三栏是理解架构的**视角**，并非互斥的产品类别。持久日志也能支持多个消费者组，从而呈现 Pub/Sub；同一组内的 Worker 分摊分区，又呈现工作队列。传统 Pub/Sub 不一定保存长时间历史；“Event Bus”也不必然是可回放的日志，须看具体产品和配置。

### 工作队列：一件事由一组 Worker 分摊

生产者发送任务，多个 Worker 竞争领取。成功后确认；失败或超时可能再次交付，所以“1-to-1”指**一次正常分配的责任归属**，不保证一条任务在故障下只执行一次。接收方仍要处理重复执行。

在 SQS 或 RabbitMQ 普通队列中，成功处理后通常删除／移除消息。在 Kafka 中，Worker 提交的是消费者组 Offset，消息仍按 Topic 的保留策略保存；要实现延迟重试、跳过坏消息或逐任务 ACK，需要额外设计。

### 发布／订阅：多个下游各自处理

生产者发布一个事件，通知服务、风控服务、统计服务各用独立订阅或消费者组接收。**独立的是订阅／消费者组，不是组内每个 Worker。** 同一组的多个 Worker 通常共同分摊，不会让每个 Worker 都处理一遍。

群聊或告警广播可帮助理解“一对多”，但群聊还涉及成员权限、离线存储和每位用户的已读位置；这些属于应用层语义，不应直接等同于消息 Broker 的订阅机制。

### 持久日志：先记录，再按位置读取

生产者把记录追加到日志，读者用 Offset 表示进度。消费者暂时不存在时，记录仍可在保留期内等待未来读取；消费者也可在保留范围内重放。Kafka 的日志通常按时间或大小保留，并非无限或永久保留。“从任意位置读取”也仅限于**仍在保留范围内**的数据。

## 三、2 × 3 框架：组合起来看

| 消息语义 \ 读取模式 | 工作队列 1-to-1 | 发布／订阅 1-to-many | 持久日志 0-to-N |
| --- | --- | --- | --- |
| **Event：已经发生** | 事件交给一个指定处理组，例如单一审计流水线 | `OrderCreated` 让风控、积分、分析各自响应 | 保存业务事件或 CDC 变更，供后来者回放 |
| **Command：需要执行** | `ResizeImage` 由一个 Worker 完成；最典型组合 | 向多个目标分别下达操作时，应拆成每个目标可独立确认的任务 | 将任务追加到 Kafka，由消费者组执行；重试、坏消息和完成状态需额外建模 |

这个框架用来**澄清需求**，不表示六个格子同样常用。`Command + 1-to-many` 尤其需要小心：如果把同一条 `SendEmail` 广播给三个消费者组，就可能发送三封邮件。更清楚的做法是先广播 `AlertRaised` 事件，再由每个渠道生成自己的 `SendSms`、`SendEmail` 等任务。

## 四、Kafka 具体如何实现两种模式？

```text
Topic: orders
  ├─ Consumer Group: risk       → 风控 Worker 共同分摊各分区
  ├─ Consumer Group: analytics  → 分析 Worker 共同分摊各分区
  └─ Consumer Group: email      → 邮件 Worker 共同分摊各分区
```

- **组与组之间**：各自维护 Offset，独立读取同一 Topic，类似 Pub/Sub 的多个订阅。
- **组的内部**：分区被分配给组内 Worker；在传统消费者组模型下，同一分区同一时刻由组内一个 Worker 消费，类似工作队列的任务分摊。可同时工作的 Worker 数量受分区数限制。
- **存储层**：消费进度与消息保留分离。提交 Offset 只改变该组下次从哪里读，不删除消息。旧消息是否可重读取决于保留策略。
- **可靠性边界**：Worker 处理成功后再提交 Offset，可降低丢任务风险，但崩溃后可能重复处理；先提交再处理则可能跳过未完成任务。外部副作用仍需幂等。

**一句话记忆**：Kafka 是日志；**同组分摊**看起来像 Queue，**多组独立读取**看起来像 Pub/Sub。选型时还要检查保留、回放、重试和顺序需求。
